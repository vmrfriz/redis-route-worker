# Протокол Redis

Для `prefix="myapp"`, `queue="preview"`, `event="newPreview"`,
`complete_event="previewReady"`:

| Объект | Имя | Содержимое |
| --- | --- | --- |
| Список заданий | `myapp_previewList` | UTF-8 строки, например JSON |
| Канал Pub/Sub | `myapp_preview` | Строки `newPreview` и `previewReady` |
| Список результатов | `myapp_previewCompleteList` | Строки, переданные в `complete()` |

Общая формула: канал `{prefix}_{queue}`, задания `{prefix}_{queue}List`,
результаты `{prefix}_{queue}CompleteList`.

## Отправка

1. Сериализовать задание в строку.
2. Выполнить `RPUSH` в список заданий.
3. Выполнить `PUBLISH` входного события в канал.

Для этих команд рекомендуется MULTI/EXEC. Никогда не отправляйте только
Pub/Sub-сообщение: событие не содержит задания. Уведомление без задания ничего
не обрабатывает. Задание без уведомления будет найдено при периодической проверке.

Воркеры читают задания через `LPOP` (FIFO извлечения). Несколько процессов с теми
же именами очередей конкурируют за задания; каждое извлечение атомарно.
Это не широковещательная доставка задания всем обработчикам.

## Получение результатов

Выполните `LPOP myapp_previewCompleteList` или блокирующий `BLPOP`.
Pub/Sub-событие завершения служит уведомлением о возможном наличии результатов.
Несколько потребителей одного списка конкурируют за результаты. Если каждому
потребителю нужна своя копия, приложение должно организовать отдельные списки.

Пакет не добавляет ID, тип, метки времени или envelope. Для сопоставления
заданий с результатами включайте свой ID в обе строки. Очистка накопленных
результатов и срок хранения находятся на стороне приложения.

## Повтор при ошибке

Исходная строка без изменения возвращается через `RPUSH`; входное событие
публикуется в той же транзакции. Нет счётчика попыток, dead-letter очереди
или задержки. Ошибка транспорта при возврате выходит из воркера и может
привести к потере извлечённого задания.
